# Состояние и дальнейшие действия

[Главная](../README.md) · [Границы проекта](IMPLEMENTATION_PLAN.md) · [Проверки](IMPLEMENTATION_PROGRESS.md)

Актуально на 21 ноября 2026 года. Основные возможности первой версии реализованы:
приём событий, общая переписка Direct и комментариев одного обращения, импорт
истории, консультации, заявки и панель администратора. Сценарии Direct проверены.
Последние изменения панели проверены автономно; прежнее подтверждение её внешнего
вида не заменяет проверку текущей версии в браузере.

## План развития и приоритеты

План верхнего уровня согласован 21 ноября 2026 года. Детализация задач, оценки
и сроки выполняются отдельно перед реализацией каждого этапа. Невыполненные пункты
описывают будущие изменения; завершённые отмечены отдельно. P0 — ближайший этап, P1 — следующий,
P2 — дальнейшие интеграции, P3 — отложенные расширения.

### P0. Подготовка VPS и управляемого выпуска версий

Использовать существующий VPS Timeweb, собственный домен и Nginx. Сохранить
инструменты mise + uv, один процесс backend и SQLite для первого размещения.

- [ ] Подготовить неинтерактивный запуск: постоянный публичный адрес из конфигурации
  вместо запроса адреса туннеля tuna. Разделить настройки local, staging и production;
  сейчас загрузчик `.env` читает только секреты.
- [ ] Подготовить запуск через systemd от отдельного непривилегированного пользователя,
  автозапуск, восстановление после сбоя и доступ к безопасным журналам. Unit-файлы
  хранить в репозитории проекта и подготовить по принятому шаблону рабочей директории.
- [ ] Настроить Nginx, DNS и HTTPS с обновлением сертификата. Приложение оставлять
  на localhost; отдельно маршрутизировать панель и webhook. Полный секретный URL
  webhook не должен попадать в журналы прокси.
- [ ] Для первого размещения текущей Streamlit-панели предусмотреть WebSocket
  и защиту входа одного пользователя через Nginx Basic Auth поверх HTTPS.
  Webhook должен иметь отдельный маршрут без Basic Auth с сохранением своей защиты;
  административный API не публиковать без предусмотренного контроля доступа.
- [ ] Разделить обновляемый код, постоянные данные, секреты и резервные копии.
  Определить перенос локальной истории либо создание новой рабочей базы.
  Подготовить резервное копирование SQLite, проверить восстановление на копии
  и выполнять изменения схемы по отдельной процедуре с возможностью отката.
- [ ] Переключить рабочий webhook на постоянный домен, проверить прежнюю регистрацию
  tuna и исключить параллельную обработку одного канала локальным и серверным backend.

Разработка и выпуск версий:

- [ ] Организовать development локально, staging и production — отдельными каталогами
  и сервисами на существующем VPS. У staging и production должны быть собственные
  окружения `.venv`, настройки, секреты и базы; данные staging не переносятся поверх
  production. Staging также закрыть от постороннего доступа.
- [ ] Предусмотреть staging без регистрации рабочего webhook и отправки сообщений
  реальным клиентам. Начать с синтетических событий; реальные интеграционные проверки
  выполнять только через отдельно согласованный тестовый канал.
- [ ] Закрепить цикл: рабочая ветка → автономные проверки → GitHub → выбранный коммит
  на staging → браузерная приёмка → тот же коммит в production → проверка запуска.
  Если после приёмки код изменился, итоговый коммит проверяется повторно.
  Сохранить существующую ветку и upstream; отдельная постоянная ветка `develop`
  для начала не обязательна.
- [ ] Подготовить повторяемые команды деплоя staging и production с фиксацией версии,
  зависимостей по `uv.lock`, проверкой работоспособности и возвратом к предыдущему
  совместимому коду. Доставка кода — через GitHub и контролируемый Git-процесс;
  рабочий production-каталог не используется для разработки.
- [ ] Начать с ручного запуска деплоя. Впоследствии автоматизировать проверки
  и доставку через GitHub Actions с ручным подтверждением production-релиза.
  Коммит, push и публикация выполняются только при соответствующем разрешении.

Текущее состояние окружений, Nginx и процедуры деплоя на сервере нужно проверить;
в рамках этой задачи обследование и настройка сервера не выполнялись.
Первое защищённое размещение Streamlit может предшествовать переносу UI;
после переноса сохраняются VPS, домен и Nginx, меняется маршрутизация интерфейса.

### P1. Переход на FastAPI + Jinja2 + HTMX

Целевая панель — серверный HTML на Jinja2, частичные обновления через HTMX
и небольшие JavaScript-модули для поведения браузера. На этом этапе остаётся
один пользователь; разделение менеджеров и роли отложены.

- [ ] Выделить интерфейс в отдельный каталог `ui/` внутри существующего Python-пакета:
  маршруты, `templates/` с фрагментами и `static/` с CSS и JavaScript.
  Сохранить существующую структуру backend и один репозиторий. Интерфейс развёртывается
  вместе с FastAPI.
- [ ] Сохранить операции с данными, консультациями и отправкой в общих функциях приложения.
  HTML-маршруты и JSON API должны использовать общую логику; шаблоны только отображают
  подготовленные данные, UI не зависит от конкретного внешнего коннектора.
- [ ] Предусмотреть вход одной учётной записи, серверную сессию, выход и CSRF-защиту
  изменяющих запросов. `ADMIN_TOKEN` остаётся серверным секретом.
- [ ] Сначала перенести сквозной сценарий: вход → выбор чата → история → ручной ответ
  → обновление результата. Затем перенести подсказки, карточку клиента, паузу, импорт,
  настройки и состояние API до функционального паритета с текущей панелью.
- [ ] Сохранить независимое обновление списка чатов, истории и подсказки; редактор
  не заменять по таймеру. Предусмотреть черновики, сохранение прокрутки, защиту
  от поздних ответов запросов при смене чата и восстановление результата отправки
  после перезагрузки без повторной отправки вслепую.
- [ ] Сначала сохранить периодический опрос API с текущими интервалами. Переход
  на SSE или WebSocket рассматривать отдельно по задержкам и нагрузке.
- [ ] Подготовить изолированные проверки нового UI, браузерную приёмку, упаковку
  шаблонов и статики и инструкцию запуска. После переключения удалить Streamlit
  и его зависимости; проверки backend сохранить, проверки Streamlit заменить.

## Ближайшая проверка текущей версии

Перед обновлением существующей установки выполните миграцию по ссылке внизу.
В браузере остаётся проверить последнюю версию панели: размещение сообщений,
прокрутку при новых сообщениях и ручной отправке, а также сохранение позиции
при чтении истории выше. Реальные API и рабочая база в автономных проверках не используются.

## Ограничения и риски эксплуатации

- Отправка с неопределённым результатом блокирует новые отправки в общей переписке.
  Автоматического повтора и ручного сброса нет: сначала нужно установить результат.
- При нескольких связанных каналах Direct панель не выбирает маршрут ручного ответа.
  Такой случай требует уточнения маршрута.
- Проверки интеграции относятся к подключённому тестовому аккаунту. Для другого
  аккаунта необходимо проверить права, каналы и сотрудника-отправителя Umnico.
- Ответы модели зависят от полноты и актуальности материалов и соблюдения инструкции.
  База знаний передаётся целиком, без поиска фрагментов. Отдельной программной
  проверки товарных утверждений нет; до проверки качества разумно использовать
  паузу с подсказками менеджеру.
- Используется один процесс backend и локальная панель одного администратора.
  Публичный доступ к панели, несколько работников backend и многопользовательская
  работа потребуют отдельной доработки.
- История импортируется только для известных приложению обращений. Автоматический
  поиск всех старых обращений не реализован.
- Фото отображается по ссылке Umnico: срок жизни ссылки и доступность изображения
  зависят от внешнего сервиса. Изображения не анализируются моделью.
- SQLite содержит переписку и контакты. Перед переносом или изменением схемы нужна
  резервная копия, а доступ к файлу базы следует ограничить.
- При смене адреса туннеля старые webhook Umnico не удаляются автоматически.
  Со временем можно достичь лимита регистраций; записи нужно проверять в Umnico.
