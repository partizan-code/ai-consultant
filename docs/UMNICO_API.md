Новые сведения об интеграции сохранять здесь, отделяя описание справочника от

Актуальное состояние основного проекта и открытые вопросы — в
[разделе 11](#11-текущее-состояние-основного-проекта).
Предоставленные 20.11.2026 карточки истории и отправки сохранены в разделах 5–6.
Разделы 1–4 и 7–10 также содержат сведения о прежнем самостоятельном прототипе:

## 0. Версия API и состояние проверки

По предоставленному пользователем фрагменту официального раздела «Прежде, чем начать»:

- Для передачи сообщений из Umnico в нашу систему необходимо настроить webhook через [отдельный метод API](https://umnico.com/ru/developers/apimethods/webhooks#doc-webhook).
- Общий синтаксис запроса: `https://api.umnico.com/version/method?parameters`.
- `version` — обязательная версия API; в общем введении последней указана `v1.3`, но предоставленные далее карточки авторизации, вебхуков и интеграций явно используют `v2`.
- `method` — обязательный путь метода из его описания в справочнике.
- `parameters` — необязательные входные параметры в виде `name=value`, разделённые `&`; состав параметров определяется конкретным методом.

Пример общего шаблона: `https://api.umnico.com/<version>/<method>?name=value`.
Это шаблон, а не готовый запрос. Версию и путь брать из карточки конкретного метода;
утверждение общего введения о `v1.3` не отменяет явно указанные пути `/v2/auth/...`, `/v2/webhooks/...` и `/v2/integrations`.

В примере исходного фрагмента приведён адрес `https://api.umnico.com/v1.3templates_waba/active`.
Между версией и методом отсутствует `/`, что противоречит описанному синтаксису.
Не использовать этот пример как подтверждение конкретного endpoint; путь метода нужно сверить отдельно.

**Подтверждено предоставленными карточками:** `/v2/auth/login`, `/v2/auth/tokens`,
`/v2/auth/plugin`, GET и POST `/v2/webhooks/`, PUT и DELETE `/v2/webhooks/{id}`,
GET `/v2/integrations` и GET `/v2/integrations/{integration-id}/mappings/users`.
Позднее получены карточки GET/POST `/v2/managers`, PUT/DELETE `/v2/managers/<id>`;
путь изменения доступа к чужим обращениям в этой карточке противоречив (раздел 2.4).
GET возвращает массив объектов вебхуков. URL и проверка формата ответа в текущем `umnico.py`
соответствуют этому описанию; оснований менять их на `v1.3` нет.
Дополнительно пользователь подтвердил успешный запуск `uv run umnico.py --login`:
POST `/v2/auth/login` и GET `/v2/webhooks/` вернули HTTP 200, список вебхуков — `[]`.

На том этапе остальные методы были сверены только с предоставленной документацией;

Позднее пользователь предоставил карточки истории и отправки: разделы 5–6 обновлены.
Метод истории подтверждён описанием; в карточке отправки найдены противоречия.

## 1. Конфигурация

Base URL: `https://api.umnico.com`

Хранить параметры в `.env`:

```ini
UMNICO_LOGIN=
UMNICO_PASSWORD=
UMNICO_API_KEY=
UMNICO_USER_ID=
UMNICO_WEBHOOK_URL=
```

Для обычных вызовов API предоставленный раздел авторизации указывает следующие заголовки:

```http
Authorization: JWT <token>
Host: api.umnico.com
```

Имя переменной проекта — `UMNICO_API_KEY`. Для текущего скрипта её значение — JWT для доступа
к API: токен из настроек API либо строка `accessToken.token` выбранного способа авторизации.
Значение можно указать с префиксом `JWT` или без него. Скрипт сохраняет уже указанный префикс,
добавляет его к значению без префикса и отклоняет `Bearer`; для обычного запроса это соответствует
предоставленному разделу справочника. `Host` HTTP-клиент формирует из URL автоматически.
Для запросов с JSON-телом использовать `Content-Type: application/json`.

`UMNICO_WEBHOOK_URL` уже используется при явной регистрации webhook, если URL не передан флагом.
`UMNICO_USER_ID` оставлен для будущего сценария отправки; текущие скрипты его не читают.
Скрипт загружает `.env` рядом с `umnico.py` с `override=False`: переменные процесса имеют приоритет.
Если заданы `UMNICO_LOGIN` и `UMNICO_PASSWORD`, обычный `uv run umnico.py` получает новый токен
без ручного ввода и использует его для обоих GET-запросов. Старый `UMNICO_API_KEY` в этом случае игнорируется.
Если задана только часть пары, недостающее значение запрашивается в терминале;
без интерактивного ввода выполнение прекращается до запросов и не переключается на старый ключ.
Пароль передаётся без удаления начальных или конечных пробелов, логин очищается от пробелов по краям.

Когда оба значения отсутствуют, обычный запуск использует `UMNICO_API_KEY`.
Флаг `--login` принудительно выбирает вход по логину и паролю: значения берутся из окружения или `.env`,
а отсутствующие запрашиваются в терминале. Пароль при ручном вводе скрывается.

### 1.1. JWT от имени аккаунта

По предоставленному описанию JWT из настроек API позволяет работать от имени всего аккаунта.
В этом же описании для получения токена приведена последовательность:

1. Открыть раздел «Авторизация и токены → Авторизация и получение токена по логину и паролю».
2. Вызвать `POST https://api.umnico.com/v2/auth/login` с JSON-полями `login` и `pass`.
3. Из ответа получить строку `accessToken.token`, которая уже содержит префикс `JWT`.
4. Использовать эту строку в заголовке `Authorization`. При ручном получении токена её можно
   записать в `UMNICO_API_KEY`; режим `umnico.py --login` сразу использует её в памяти процесса.

`accessToken` — объект, а не строка. Нельзя копировать в переменную окружения весь объект
или обращаться с ним как с готовым значением заголовка.

### 1.2. OAuth 2 от имени пользователя

Справочник также описывает авторизацию от имени конкретного пользователя двумя способами.

**Через plugin token:**

1. [Зарегистрировать плагин](https://umnico.com/ru/developers/apimethods/plugins#plugin-register)
   и получить `pluginToken`. Для этого шага в предоставленном тексте указан заголовок
   `Authorization: bearer <JSON Web Token>` и `Host: api.umnico.com`.
2. Вызвать [метод авторизации по plugin token](https://umnico.com/ru/developers/apimethods/auth#doc-plugin),
   чтобы получить временный `accessToken`.
3. В обычных вызовах API передавать строку `accessToken.token` в заголовке `Authorization`.
   Эта строка уже содержит префикс `JWT`.
4. При `401`, вызванном истечением `accessToken`, повторить авторизацию по plugin token
   и использовать новый `accessToken`.

`pluginToken` служит для получения `accessToken`; не подставлять его вместо `accessToken`
в текущую проверку вебхуков. Пример с `bearer` относится к отдельному шагу регистрации плагина,
а не к обычным запросам API.

**Через логин и пароль:**

1. Вызвать [метод авторизации](https://umnico.com/ru/developers/apimethods/auth#doc-login)
   и получить `accessToken` и `refreshToken`.
2. В обычных вызовах API передавать строку `accessToken.token` в заголовке `Authorization`.
3. При истечении `accessToken` вызвать [метод обновления токенов](https://umnico.com/ru/developers/apimethods/auth#doc-tokens)
   с заголовком `Authorization`, равным строке `refreshToken.token`, включая `JWT`.
4. Сохранить возвращённые `accessToken.token` и `accessToken.expiresAt`; если ответ также содержит
   обновлённый `refreshToken`, сохранить его `token` и `expiresAt`. Согласно общему описанию,
   сервер может обновить `refreshToken`, если его срок подходит к концу.
5. Если обновление возвращает `401`, снова выполнить авторизацию по логину и паролю.

Роли токенов:

| Токен | Назначение | Использование в `umnico.py` |
|---|---|---|
| JWT из настроек API / `accessToken.token` | Доступ к обычным методам API с `Authorization: JWT ...` | Строковое значение `UMNICO_API_KEY` |
| `refreshToken.token` | Получение нового `accessToken` через специальный метод обновления | Не передавать в проверку вебхуков |
| `pluginToken` | Получение временного `accessToken` через метод авторизации по plugin token | Не передавать в проверку вебхуков |

Получение нового токена реализовано при заданных `UMNICO_LOGIN` / `UMNICO_PASSWORD`
или по явному запуску `umnico.py --login`.
Обновление через `refreshToken`, сохранение токенов и автоматический повтор входа не реализованы.
Login выполняется без заголовка `Authorization` по примеру с логином и паролем;
этот вариант подтверждён успешным пользовательским запуском на реальном аккаунте.
Не добавлять в документацию значения токенов, логины и пароли пользователя.

### 1.3. Точные методы авторизации и структура ответов

Все следующие сведения взяты из карточек методов, предоставленных пользователем.
Имена полей чувствительны к написанию: пароль передаётся в `pass`, не в `password`.

**Login:** `POST https://api.umnico.com/v2/auth/login`.

JSON-тело запроса (условные значения):

```json
{
    "login": "user@example.com",
    "pass": "<password>"
}
```

Структура успешного ответа (токены и даты заменены обозначениями):

```json
{
    "accessToken": {
        "token": "JWT <access-token>",
        "expiresAt": "<ISO 8601 date-time>"
    },
    "refreshToken": {
        "token": "JWT <refresh-token>",
        "expiresAt": "<ISO 8601 date-time>"
    }
}
```

**Неоднозначность справочника:** в таблице login заголовок `authorization` с `accessToken`
отмечен обязательным, но в примере приведён только JSON с логином и паролем.
В `umnico.py --login` реализован вариант без `Authorization`, соответствующий примеру запроса.
Пользователь подтвердил HTTP 200 при таком входе: для проверенного сценария предварительный
токен не потребовался. Противоречие таблицы и примера сохраняется в самом справочнике,
но больше не блокирует этот сценарий авторизации.

**Обновление:** `POST https://api.umnico.com/v2/auth/tokens`.

- Обязательный заголовок `authorization`: строка `refreshToken.token`, уже включающая `JWT`.
- В примере запроса тело не указано.
- Ответ содержит объект `accessToken` с обязательными строковыми полями `token` и `expiresAt`.
- Отсутствие нового `refreshToken` в ответе не является ошибкой: сохранить прежний.

**Plugin token:** `POST https://api.umnico.com/v2/auth/plugin`.

- Таблица требует заголовок `authorization` со значением действующего `accessToken`
  (в заголовок передаётся его строка `token`).
- Обязательные поля тела: `pluginToken` — строка, `manager` — строковый ID менеджера.
- Ответ содержит объект `accessToken` с обязательными строковыми полями `token` и `expiresAt`.
- Это отдельный метод от регистрации плагина. Заголовок `bearer` из описания регистрации
  не переносить автоматически на `/v2/auth/plugin`.
- Получение исходного `accessToken`, требуемого таблицей этого метода, остаётся вопросом
  для сверки полного сценария авторизации плагина.

Для `UMNICO_API_KEY` нужно скопировать именно строку вида `JWT ...` из `accessToken.token`:

```ini
UMNICO_API_KEY="JWT <access-token>"
```

`<access-token>` здесь — обозначение, а не рабочий токен. Значения из примеров справочника
не являются данными нашего аккаунта. Срок действия брать из реального `expiresAt`,
а не из демонстрационных дат. Срок действия токена из настроек API этим описанием не установлен.

### 2.1. Интеграции аккаунта

`GET https://api.umnico.com/v2/integrations`.

Обязательный заголовок `Authorization`: строка `accessToken.token`, включая `JWT`.
Успешный ответ — массив объектов интеграций со следующими полями по таблице справочника:

| Поле | Тип | Назначение |
|---|---|---|
| `id` | integer | Идентификатор интеграции |
| `type` | string | Тип подключённой интеграции |
| `login` | string | Логин в мессенджере или название аккаунта в социальной сети |
| `avatar` | string | Аватар подключённого аккаунта |
| `externalId` | string | Идентификатор подключённого аккаунта во внешней системе |
| `status` | string | Статус интеграции; в примере — `active` |
| `identifier` | string | Идентификатор для сопоставления каналов одного внешнего аккаунта |
| `url` | string или null | Ссылка на интеграцию |

Все поля отмечены в таблице обязательными, при этом `url` допускает null.
Пример с условными данными, сохраняющий особенности предоставленного примера:

```json
[
    {
        "id": 75,
        "type": "whatsapp",
        "login": "example-account",
        "avatar": "https://example.com/avatar.jpg",
        "externalId": "example-external-id",
        "status": "active",
        "url": "https://example.com/account"
    }
]
```

Типы, перечисленные в предоставленном разделе:

| `type` | Интеграция |
|---|---|
| `vkGroup` | Группа ВКонтакте |
| `telebot` | Telegram-бот |
| `whatsapp2` | WhatsApp |
| `widget` | Виджет Umnico |
| `telegram` | Telegram-personal |
| `max` | MAX |
| `waba` | WhatsApp Business API |
| `viberBot` | Viber |
| `ok` | Одноклассники |
| `avito` | Avito |
| `mailbox` | Mailbox |
| `autoru` | Auto.ru |

Расхождения и правила интерпретации:

- Пример возвращает `type: "whatsapp"`, хотя в перечне указан `whatsapp2`.
  Не заменять одно значение другим автоматически и не использовать перечень как строгий закрытый набор типов.
- В примере отсутствует `identifier`, несмотря на обязательность в таблице.
  Отсутствие этого поля учитывать при обработке фактических ответов.
- Типы I-Gram Директ и I-Gram Комментарии в перечне не названы.
  Не определять Instagram по выдуманному значению `type` или только по префиксу `instagram`;
  сначала получить реальные значения из списка интеграций и событий.
- В реальном ответе проверенного аккаунта пользователь подтвердил тип `instagramV3`
  со статусом `active` и присутствующим `identifier`. Последующее входящее сообщение
  также подтвердило `message.sa.type: "instagramV3"` для этого канала.
  Не распространять этот тип автоматически на все варианты Instagram и I-Gram.
- `status` интеграции — строка; не путать его с числовым `status` вебхука.

`identifier` позволяет связать разные каналы одного аккаунта: у I-Gram Директ и I-Gram Комментарии
могут различаться `source.id` и `saId`, но совпадать `identifier`.
Это используется для выбора канала ответа в директ из комментариев, когда подключено несколько
интеграций I-Gram Директ. Совпадение `identifier` не делает `source.id` и `saId` взаимозаменяемыми;
при отправке сохранять идентификаторы выбранного канала.

Метод списка интеграций позволяет изучить подключённые каналы после успешной авторизации.
Он сам по себе не подтверждает приём и доставку сообщений и не устраняет `401` с тем же токеном.
Текущий `umnico.py` вызывает этот метод после успешного GET вебхуков с тем же токеном.
Выводятся общее количество интеграций и для каждой записи поля `id`, `type`, `login`, `status`
и `identifier`. Если поле отсутствует, в краткой записи оно выводится как null.
Неизвестный `type` и отсутствие `identifier` не считаются ошибкой и не заменяются догадками.
Пустой массив вызывает предупреждение об отсутствии подключённых каналов, но не ошибку авторизации.

### 2.2. Сопоставления пользователей интеграции

`GET https://api.umnico.com/v2/integrations/{integration-id}/mappings/users`.

- `integration-id` — обязательный integer в пути, идентификатор интеграции в Umnico.
- Заголовок `Authorization` содержит строку `accessToken.token`, включая `JWT`.
- Метод работает **только для интеграций с amoCRM и «МойСклад»**; не использовать его
  как универсальный способ получения `userId` для Instagram.
- Ответ — объект: ключ соответствует ID пользователя внешней системы, значение — integer ID пользователя Umnico.
- Обязательное поле `default` — integer ID владельца аккаунта Umnico.

Пример с условными идентификаторами:

```json
{
    "3389846": 1,
    "3385134": 2,
    "default": 1
}
```

Ключи ID в JSON представлены строками, значения — числами.
`default` обозначает владельца аккаунта, а не автоматически выбранного сотрудника для отправки.
Не подставлять его в `UMNICO_USER_ID` без выбора нужного сотрудника и подтверждения контекста интеграции.

### 2.3. Сотрудники аккаунта и userId для отправки

Источник: предоставленная пользователем 20.11.2026 карточка «Сотрудники».
Подтверждено её описание, а не реальный ответ текущего аккаунта.

`GET /v2/managers` — список всех сотрудников аккаунта. Обязательный заголовок
`authorization` содержит accessToken; формат обычной авторизации JWT описан в разделе 1.
Успешный ответ — массив объектов сотрудников.

| Поле | Тип/обязательность по карточке | Значение |
| --- | --- | --- |
| `id` | integer, обязательное | ID сотрудника Umnico |
| `name` | string, обязательное | Название организации либо имя пользователя |
| `login` | string, обязательное | Email сотрудника; не выводить в общедоступные логи |
| `role` | string, необязательное | `owner` или `manager` |
| `confirmed` | boolean, обязательное | Подтверждён ли аккаунт сотрудника |
| `allowAllDeals` | boolean или null | Доступ ко всем обращениям операторов в пределах доступных интеграций |
| `sources` | массив объектов; отметка `Да /` неоднозначна | Доступы к интеграциям |
| `metadata` | object, допускается `{}` | Данные внешней системы при импорте пользователя |

Запись в `sources` содержит необязательные `id` (integer, ID записи доступа) и
`saId` (integer или null, ID интеграции). `sources: []` означает доступ ко всем
интеграциям. Карточка трактует `saId: null` как отсутствие доступа ко всем интеграциям;
при создании явно описан вариант единственной записи `[{"saId": null}]`.
Смешанный набор null и конкретных saId отдельно не разъяснён.

Сокращённый пример с условными ID:

```json
[
    {
        "id": 15,
        "login": "owner@example.org",
        "name": "Владелец",
        "role": "owner",
        "confirmed": true,
        "allowAllDeals": false,
        "allowedUsers": null,
        "sources": [],
        "metadata": {}
    },
    {
        "id": 18,
        "login": "manager@example.org",
        "name": "Менеджер",
        "role": "manager",
        "confirmed": true,
        "allowAllDeals": false,
        "allowedUsers": null,
        "sources": [{"id": 27, "saId": 88}],
        "metadata": {}
    }
]
```

В оригинальном примере metadata содержит `source: amocrm`, `externalId` и объект
`amocrm` с email. Это сведения о внешней системе, а не замена ID сотрудника Umnico.
Поле `allowedUsers` присутствует в примерах со значением null, но отсутствует в
таблице GET; значение null для прав на чужие обращения отдельно не разъяснено.

**Для отправки:** `userId` берётся из **`id` выбранного сотрудника** этого списка.
Не путать его с `sources[].id`, `saId`, metadata.externalId, customerId или sender.id.
Нужно явно выбрать сотрудника, проверить его `confirmed`, доступ к нужной интеграции
и обращениям. Пустой sources разрешает все интеграции, но сам по себе не означает
доступ ко всем чужим обращениям. Не выбирать первую запись/owner автоматически.
В текущем проекте числовой ID задаётся через `Settings.umnico_user_id` в Python
(поле хранит строку, клиент преобразует её в integer); в `.env` его не добавлять.
Позднее пользователь предоставил результат реального GET: найден подтверждённый
owner с ID `2583899`, sources пустой (раздел 11.5). Пользователь затем подтвердил
доставку тестового сообщения с этим userId; он явно задан в настройке приложения.
Это выбор для текущего аккаунта. Доступ ко всем другим обращениям нельзя считать
подтверждённым только по пустому sources.

### 2.4. Администрирование сотрудников — справочно

Все методы требуют accessToken. Они сохранены по той же карточке, но не нужны для
чтения списка и выбора отправителя; код бота не должен создавать, удалять сотрудников
или менять права автоматически. Реальные вызовы этих методов не выполнялись.

| Действие | Метод и путь карточки | Тело/результат |
| --- | --- | --- |
| Пригласить сотрудника | `POST /v2/managers` | `login` (email приглашения), `sources`; ответ — массив сотрудников |
| Изменить доступы к интеграциям | `PUT /v2/managers/<id>` | `sources` с записями доступа; HTTP 200 и пустое тело |
| Изменить доступ к чужим обращениям | `PUT /v2/managers/<id>/permissions` | `allowedUsers` — массив ID сотрудников; HTTP 200 и пустое тело |
| Удалить сотрудника | `DELETE /v2/managers/<id>` | ID сотрудника в пути; HTTP 200 и пустое тело |

- Создание отправляет приглашение на указанный login. `sources: []` даёт доступ ко
  всем интеграциям; единственная запись `{"saId": null}` — ни к одной.
  Таблица POST называет тип sources строкой, но описание и пример используют массив
  объектов. Это противоречие, а не основание сериализовать массив в JSON-строку.
- В ответе создания есть пример нового сотрудника с `name: null` и
  `confirmed: false`, хотя таблица GET описывает обязательное строковое name.
  Примеры POST также опускают sources/metadata, поэтому не переносить на них
  без проверки строгую обязательность полей таблицы GET.
- Для PUT доступов таблица отмечает login обязательным, но пример передаёт только
  sources. В примере существующая запись содержит id и saId, новая — только saId.
  Требование login и точные правила обновления массива необходимо уточнить перед использованием.
- Для прав на чужие обращения путь противоречив: карточка указывает
  `/v2/managers/<id>/permissions`, пример — `/v2/managers/users-access/<id>`.
  Корректный путь не установлен. Нельзя пробовать оба пути автоматически.
- `allowedUsers: []` означает отсутствие доступа к обращениям других сотрудников.
  Каждый вызов **перезаписывает** массив: после `[1, 2, 3]`, затем `[1]` останется `[1]`.
  В примере тело — `{"allowedUsers": [15]}`; ID здесь принадлежат сотрудникам,
  к обращениям которых предоставляется доступ.
- Пустое тело успешных PUT/DELETE нельзя разбирать через `.json()`.
  Для первого этапа достаточно только GET списка сотрудников; запись прав и удаление
  не входят в реализацию текстовой интеграции.

## 3. Вебхуки

Для всех четырёх методов требуется заголовок `Authorization` со строкой `accessToken.token`,
включающей `JWT`. Карточки GET и POST указывают `/v2/webhooks/` с завершающим `/`,
а примеры URL — `/v2/webhooks` без него. Скрипт использует путь из карточки с `/`;
для него пользователь подтвердил HTTP 200. Вариант без `/` и перенаправления отдельно не проверялись.

### 3.1. Получение списка

`GET https://api.umnico.com/v2/webhooks/`.

Успешный ответ — массив объектов. Пустой массив `[]` означает отсутствие записей;
это допустимый результат, а не ошибка авторизации или доказательство отсутствия Instagram.
Пример с условными данными:

```json
[
    {
        "id": 1,
        "url": "https://example.com/webhooks/umnico",
        "name": "Python Test Bot",
        "status": 1
    }
]
```

Объект вебхука описан в справочнике следующими полями:

| Поле | Тип | Описание |
|---|---|---|
| `id` | integer | Идентификатор записи |
| `url` | string | Адрес получения событий |
| `name` | string | Пользовательское имя |
| `status` | integer | Статус активности, значения 0 или 1 |
| `events` | array | Выбранные события; в примерах ответов поле отсутствует |

Не считать отсутствие `events` ошибкой формата: сами примеры GET, POST и PUT его не содержат.

### 3.2. Создание

`POST https://api.umnico.com/v2/webhooks/`.

| Поле JSON-тела | Тип | Обязательность по таблице |
|---|---|---|
| `url` | string | Нет; для нашего тестового получателя указать публичный HTTPS-адрес |
| `name` | string | Нет |
| `events` | array | Отмечено «Да /», но в примере запроса отсутствует |

По описанию `events: []` включает все события, а непустой массив ограничивает их перечисленными.
Чтобы явно выбрать все события для первого этапа наблюдения, тело можно сформировать так:

```json
{
    "url": "https://example.com/webhooks/umnico",
    "name": "Python Test Bot",
    "events": []
}
```

Это вариант на основе описания `events`, а не выполненный запрос. Предоставленный пример
справочника содержит только `url` и `name`. Поведение при отсутствии `events` явно не установлено;
не считать его эквивалентным пустому массиву без проверки.
Предоставленная карточка не перечисляет допустимые названия событий. Последующий пользовательский
запуск подтвердил получение `customer.created`, `lead.created`, `lead.changed` и `message.incoming`.
Позднее подтверждён также приём `message.outgoing` (раздел 11.5).
Работа фильтрации по непустому `events` ещё не проверена.

Успешный ответ — созданный объект вебхука по схеме из раздела 3.1.
Не требовать наличия `events`, если сервер вернул объект по примеру справочника.

Ограничения, подтверждённые предоставленным описанием:

- Одновременно можно создать не более 10 вебхуков.
- При попытке создать 11-й сервер возвращает HTTP 400 BAD REQUEST и тело:

```json
{
    "error": "Only 10 servers can be created"
}
```

- При недоступности адреса `url` вебхук может быть отключён; Umnico уведомляет об этом по email.

Перед созданием сначала получить список и проверить наличие записи с тем же URL,
чтобы избежать дублирования. Существующие вебхуки не изменять и не удалять.
Логирование всех событий на первом этапе не должно запускать автоматические ответы.

### 3.3. Изменение

`PUT https://api.umnico.com/v2/webhooks/{id}`, где `id` — integer в пути.

- Необязательные поля: `url` и `name` типа string, `status` со значениями 0 или 1.
- В таблице запроса `status` указан как string, а в ответах — integer;
  не переносить тип ответа на тело PUT без сверки. Наш скрипт PUT не выполняет.
- `events` — массив с той же неоднозначностью обязательности и тем же описанием пустого массива,
  что у POST. В предоставленном примере PUT поле также отсутствует.
- Успешный ответ — изменённый объект вебхука по схеме из раздела 3.1.

### 3.4. Удаление

`DELETE https://api.umnico.com/v2/webhooks/{id}`, где `id` — integer в пути.

Успех — HTTP 200 OK без тела ответа. При реализации этого метода не вызывать `.json()`
для пустого ответа. Текущий `umnico.py` не выполняет DELETE; создание включается только явным флагом.

## 4. Входящие события

Umnico отправляет POST-запрос на зарегистрированный URL.

Все примеры ниже сокращены и обезличены. Они отражают предоставленные пользовательские логи,
а не полную обязательную схему API: поля могут отсутствовать, иметь null или расширяться.
Текущий получатель только маскирует секреты и логирует JSON; извлечение полей и маршрутизация
из этого раздела ещё не реализованы в коде.

### 4.1. Сообщение в Direct

Подтверждённая пользовательским логом структура `message.incoming`.
Ниже ID, идентификатор сообщения и текст заменены условными значениями;
профили, аватар и персональные данные не копируются:

```json
{
    "type": "message.incoming",
    "accountId": 123,
    "leadId": 456,
    "message": {
        "messageId": "<message-id>",
        "datetime": "2026-11-20T10:49:45.523Z",
        "incoming": true,
        "sa": {
            "id": 88,
            "type": "instagramV3"
        },
        "source": {
            "id": "external-sender-id",
            "realId": 255,
            "type": "message",
            "saId": 88,
            "identifier": "<account-identifier>",
            "token": "[REDACTED]"
        },
        "message": {
            "text": "Привет!"
        }
    },
    "isNewLead": true,
    "isNewCustomer": true,
    "webhookId": "<event-webhook-id>"
}
```

Подтверждённые пути полей:

| Путь от корня JSON | Значение и назначение |
|---|---|
| `type` | `message.incoming` |
| `leadId` | Числовой ID обращения |
| `message.incoming` | true для полученного входящего сообщения |
| `message.messageId` | Строковый ID сообщения |
| `message.datetime` | Время сообщения в UTC в формате ISO 8601 |
| `message.message.text` | Текст сообщения |
| `message.sa.id` | Числовой ID интеграции, совпавший с `id` списка интеграций в проверенном случае |
| `message.sa.type` | `instagramV3` для проверенного канала |
| `message.source.realId` | Числовой внутренний ID источника; приоритетный `source` в первоначальном сценарии API |
| `message.source.id` | Строковый внешний идентификатор; в проверенном Direct совпал с `message.sender.socialId`, для комментария имеет другой формат |
| `message.source.saId` | ID интеграции источника; в полученном событии совпал с `message.sa.id` |
| `message.source.identifier` | Строковое значение, совпавшее с `identifier` ранее полученной интеграции |

`source.token` маскируется получателем и не требуется для текущего API-клиента:
для авторизации используется собственный `accessToken.token`, полученный через login.
Не восстанавливать `source.token` из лога и не подставлять вместо токена доступа к API.

В том же пользовательском тесте получены отдельные события:

- `customer.created`: содержит `customerId` и объект `customer`.
- `lead.created`: содержит `leadId` и объект `lead`; `lead.socialAccount.type` равен `instagramV3`.
  Краткий текст последнего сообщения расположен в `lead.message.data.text`, что отличается
  от пути текста в событии `message.incoming`.
- В `lead.created` поле `lead.userId` равно null. ID сотрудника для отправки этим событием не установлен;
  `customerId`, `message.sender.id` и `message.sender.socialId` не заменяют `UMNICO_USER_ID`.

Наблюдаемый верхнеуровневый `webhookId` — строка UUID, различавшаяся между тремя событиями.
Не считать её числовым `id` записи из GET `/v2/webhooks/` и не использовать для PUT/DELETE записи.
Назначение этого UUID отдельно не подтверждено.

На первом этапе сохранять полученные JSON-события в лог и возвращать HTTP 200.

### 4.2. Комментарий к посту Instagram

20.11.2026 пользователь получил `message.incoming` с `message.source.type: "comment"`.
Текст комментария находился в `message.message.text`, ссылка на пост — в `message.message.url`.
Дополнительно присутствовал объект `message.preview` с изображением, описанием и владельцем поста.
Условный пример сохраняет структуру наблюдаемого события:

```json
{
    "accountId": 123,
    "leadId": 456,
    "type": "message.incoming",
    "message": {
        "messageId": "<comment-message-id>",
        "datetime": "2026-11-20T10:54:54.000Z",
        "incoming": true,
        "sa": {
            "id": 88,
            "type": "instagramV3"
        },
        "message": {
            "text": "Тестовый комментарий",
            "url": "https://www.instagram.com/p/EXAMPLE/"
        },
        "sender": {
            "id": 901,
            "customerId": 902,
            "login": "example_sender",
            "type": "instagramV3",
            "socialId": "external-sender-id",
            "profileUrl": "https://www.instagram.com/example_sender/"
        },
        "source": {
            "id": "external-media-id_external-owner-id",
            "realId": 256,
            "name": "Сокращённое описание поста",
            "type": "comment",
            "saId": 88,
            "sender": "external-sender-id",
            "identifier": "<account-identifier>",
            "token": "[REDACTED]"
        },
        "preview": {
            "photo": "https://example.com/post-preview.jpg",
            "description": "Описание поста",
            "owner": "example_owner",
            "url": "https://www.instagram.com/p/EXAMPLE/"
        },
        "replyTo": null
    },

    "isNewCustomer": false,

```

| Путь | Наблюдаемое назначение |
|---|---|
| `message.source.type` | `comment`; отличает комментарий от Direct с `type: "message"` |
| `message.message.text` | Текст комментария, а не подпись к посту |
| `message.message.url` | Ссылка на пост, к которому относится комментарий |
| `message.preview.url` | В проверенном событии та же ссылка на пост |
| `message.preview.photo` | URL изображения превью; содержимое изображения отдельно не проверялось |
| `message.preview.description` | Описание поста из события, в отличие от текста комментария |
| `message.preview.owner` | Имя аккаунта владельца поста |
| `message.source.name` | В наблюдаемом событии сокращённое описание; не заменяет `preview.description` |
| `message.messageId` | ID конкретного сообщения/комментария; даже если состоит из цифр, сохранять строкой |
| `message.source.id` | Составной внешний ID источника; хранить целиком как непрозрачную строку |

Direct и комментарий пришли с одинаковыми `accountId`, `leadId`, `message.sa.id`,
`message.sa.type: "instagramV3"` и `source.identifier`, но с разными `source.realId`,
`source.id` и `source.type`. Поэтому `leadId` или `sa.type` по отдельности недостаточны
для выбора контекста обработки. Не заменять источник комментария ранее сохранённым источником Direct.
Не выводить из формата составного `source.id` универсальное правило построения ID API.

Для определения поста в таком событии достаточно URL из `message.message.url`;
при его отсутствии можно проверить `message.preview.url`. Короткий код в пути `/p/<shortcode>/`
идентифицирует ссылку на пост, но не равен внутреннему `source.realId` или `messageId`.
Превью наблюдалось у комментария; его наличие во всех сообщениях не гарантировано.
Срок действия ссылок `preview.photo` не установлен, поэтому их не считать постоянным хранилищем медиа.

### 4.3. Изменение обращения и ссылка на пост в тексте

Пользователь также получил `lead.changed` после нового входящего сообщения.
Сокращённая структура с условными значениями:

```json
{
    "accountId": 123,
    "leadId": 456,
    "type": "lead.changed",
    "lead": {
        "id": 456,
        "userId": null,
        "socialAccount": {
            "id": 88,
            "type": "instagramV3"
        },
        "message": {
            "unread": 2,
            "timestamp": "2026-11-20T10:52:16.463Z",
            "incoming": true,
            "data": {
                "text": "https://www.instagram.com/p/EXAMPLE/?cnvx=example"
            }
        }
    },
    "webhookId": "<event-webhook-id>"
}
```

В этом событии `lead.message.data.text` содержал ссылку на тот же пост, который позднее
присутствовал в событии комментария. По такой ссылке виден пост, но самого изображения,
подписи, `messageId` и `source.realId` в присланном `lead.changed` нет.
Не восстанавливать их догадками и не считать текст ссылки доказательством комментария:
для него подтверждающий признак — `message.source.type: "comment"` в `message.incoming`.
Параметр `cnvx` не входит в короткий код поста; исходный URL можно сохранять целиком,
а для сопоставления проверенных ссылок `/p/.../` отдельно выделять код из пути.

`lead.created` и `lead.changed` содержат состояние обращения и краткие сведения о последнем
сообщении. При будущей обработке использовать `message.incoming` как событие входящего сообщения,
а события обращения — для обновления его состояния. Не запускать повторный ответ на тот же текст
из `lead.changed`. Порядок доставки, повторы и полнота событий официально здесь не установлены.

## 5. Получение истории переписки

Источник: предоставленная пользователем 20.11.2026 карточка «История сообщений».
Сведения карточки отделены ниже от последующей пользовательской проверки каналов.
Первая страница истории Direct впоследствии получена пользователем; её метаданные
сохранены в разделах 5.2 и 11.5. Импорт в приложение ещё не проверен.

### 5.1. Получение каналов обращения

Подтверждённый пользовательской проверкой путь:
`GET /v2/messaging/<lead-id>/threads`.

Предоставленная карточка указывает `GET /v2/leads/<lead-id>/threads`, но для
обращения `69258224` этот вариант вернул HTTP 404, тогда как вариант `messaging`
вернул массив каналов. Для чтения каналов в этом аккаунте использовать проверенный
вариант `messaging`; не добавлять автоматический перебор путей. Подробности — раздел 11.5.

- Заголовок `authorization`: токен доступа; формат `JWT <token>` установлен
  ранее предоставленным разделом авторизации.
- `lead-id` — обязательный integer, ID обращения.
- Карточка указывает источник ID обращения: `GET /v2/leads/?category={inbox|all}`,
  массив обращений, поле `id`. `inbox` — входящие, `all` — все обращения.
  Полная карточка списка обращений и его пагинации пока не предоставлена.
- Ответ — массив каналов сообщения. Все ID в приведённых далее примерах условные.

| Поле канала | Тип по карточке | Назначение |
| --- | --- | --- |
| `id` | string, обязательное | Идентификатор канала в социальной сети/мессенджере |
| `realId` | integer, обязательное | Внутренний ID канала Umnico |
| `name` | string или null | Название поста/фотографии/комментария |
| `type` | string, обязательное | Тип канала |
| `saId` | integer, обязательное | ID интеграции |
| `sender` | string, обязательное | ID клиента в социальной сети/мессенджере |
| `token` | string или null | Токен канала; не логировать и не подменять им accessToken |
| `identifier` | string, обязательное | Идентификатор социальной сети/мессенджера |
| `expiresAt` | string date-time или null | Срок ответа на последнее сообщение |

Типы: `comment`, `message`, `photo`, `video`, `market` — соответственно комментарий
к посту, сообщение, комментарий к фотографии, видеозаписи или товару.
В примерах отсутствует `expiresAt`, хотя таблица помечает его как обязательное/null.
В реальном диагностическом выводе есть также запись с `realId: None` и
`expiresAt: None`. Блок выводит значения через `.get()`, поэтому он не различает
отсутствующее поле и явный JSON null. Нельзя считать каждую запись пригодной для
истории: проверка выполняется на канале с известным положительным realId.
Внешний `id` этой записи не выводился; возможность его использования для отправки
по карточке не означает допустимость подстановки в endpoint истории.

Карточка перечисляет `comment` для avito/autoru, `message` для viberBot, whatsapp2,
telegram, telebot, mailbox, widget, waba, ok и оба типа для vkGroup. Instagram в этом
перечне отсутствует. Это не отменяет ранее наблюдавшиеся `instagramV3` и
`source.type: message/comment`; список нельзя использовать как полный запрет этих каналов.

Пример сокращённой записи канала:

```json
{
    "id": "external-channel-id",
    "realId": 255,
    "name": null,
    "type": "message",
    "saId": 88,
    "sender": "external-customer-id",
    "token": null,
    "identifier": "account-identifier"
}
```

`sender` — клиент, а не сотрудник Umnico. Этот метод не определяет `userId` для отправки;
список сотрудников и их ID описан в разделе 2.3.

### 5.2. История отдельного канала

`POST /v2/messaging/<lead-id>/history/<source-real-id>`.

- `lead-id` и `source-real-id` — обязательные integer в пути.
- `source-real-id` берётся из `realId` выбранного канала раздела 5.1.
- Необязательный `cursor` в JSON-теле — **integer**. При первом запросе его не передавать.
- Возвращённый `cursor` нужен для запроса более ранних сообщений.

Пользовательская проверка POST `/v2/messaging/69258224/history/81937872` с телом
`{}` вернула source `81937872`, integer cursor `1795171785523` и три сообщения.
У всех трёх присутствуют `messageId`, `sentAt` и `incoming`; `datetime` отсутствует.
Значения sentAt имеют тип str, однако диагностический блок не выводил и не разбирал
их содержимое: ISO 8601 и единицы времени пока не подтверждены. Наличие messageId
в этой странице не отменяет его необязательность в карточке и не доказывает
совпадение с ID входящего webhook. Большое значение cursor нужно передавать целиком
как JSON integer, без преобразования в строку или трактовки как номера страницы.

Последующий пользовательский запрос с `{"cursor": 1795171785523}` вернул
`source: 0`, `cursor: 0`, `messages: []` (выведено MESSAGES_COUNT `0`). Cursor
изменился, поэтому завершение по правилу «cursor не изменился» этот случай не
обнаруживает. Для проверенного канала наблюдаемый признак конца — пустая страница
с нулевыми source и cursor. Это наблюдение одного канала, а не гарантия для всех
типов интеграций и пустых ответов.

Тело первого запроса:

```json
{}
```

Пример последующего запроса: `{"cursor": 1}`. Пример формы ответа:

```json
{
    "cursor": 60,
    "source": 255,
    "messages": [
        {
            "sentAt": "2020-09-29T11:19:54.279Z",
            "sa": {"id": 88, "type": "vkGroup"},
            "incoming": true,
            "message": {"text": "Пример сообщения"},
            "source": {
                "id": "external-channel-id",
                "realId": 255,
                "type": "message",
                "saId": 88,
                "sender": "external-customer-id",
                "token": null
            },
            "preview": null
        }
    ]
}
```

Пример сокращён и обезличен; он иллюстрирует форму, а не реальную переписку.

| Поле ответа | Тип по карточке | Назначение |
| --- | --- | --- |
| `cursor` | integer, обязательное | Смещение для следующего запроса |
| `source` | integer, обязательное | Внутренний ID канала, аналог `source-real-id` |
| `messages` | массив | Сообщения; отметка обязательности в таблице неоднозначна (`Да /`) |

Поля отдельного сообщения помечены необязательными:

- `sentAt`: string date-time; пример ISO 8601. Описание одновременно называет это
  Unix-временем в миллисекундах — противоречие не устранено. Поля `datetime` в этой
  карточке истории нет, хотя оно наблюдалось во входящем webhook.
- `sa`: данные интеграции; в примере `id`, `type`, `login`, `avatar`.
- `incoming`: boolean, true для входящего, false для исходящего.
- `message`: `text`, `url`, `attachments`. Вложение содержит `type`, `url`, `text`,
  `preview`, `filesize`; у кнопки также `data` (callbackData) и `caption`.
- `sender`: `id`, `customerId`, `login`, `avatar`, `type`, `socialId`, `profileUrl`.
  `sender.id` описан как ID профиля клиента либо externalId интеграции; это не
  подтверждение ID сотрудника для параметра отправки `userId`.
- `preview`: `photo`, `description`, `owner`, `url`; может быть null.
- `source`: объект канала из раздела 5.1. В примере внутри сообщения отсутствует
  `identifier`, хотя таблица канала требует его.
- `messageId`: string, необязательное. В обоих примерах сообщений истории отсутствует.
- `customId`: string, по описанию возвращается только в исходящем webhook.
  Рассчитывать на его наличие в загруженной истории нельзя.
- `replyTo`: цитата с `messageId` (integer), `sentAt`, `incoming`, `preview`, `sender`,
  `message`; вложенный `message` содержит текст, URL и те же поля вложений.

Типы вложений: `photo`, `doc`, `link`, `video`, `audio`, `sticker`, `market`, `mail`, `button`.

### 5.3. Реализованная адаптация и ограничения

- Cursor передаётся как integer; bool, строка и нулевой cursor запроса отклоняются
  до обращения к API. Лимит страниц и повторный cursor предотвращают цикл.
- Для непустой страницы source должен совпадать с запрошенным realId. Пустая
  страница `messages: [], source: 0, cursor: 0` завершает импорт; следующий запрос
  с нулевым cursor не выполняется. Другие формы пустого ответа отклоняются.
- Отдельный `parse_history_message` читает sentAt, а webhook продолжает читать
  datetime. Поддержаны ISO 8601 с часовым поясом и Unix-миллисекунды (integer либо
  строка ASCII-цифр); время приводится к UTC. Это поддержанные форматы адаптера,
  а не утверждение о конкретном содержимом невыведенных реальных sentAt.
- Необязательные source/sa берутся из проверенного маршрута страницы, а явно
  переданные идентификаторы проверяются. Несовпадение канала отклоняется.
- Без messageId страница не сохраняется: ошибка `history_message_id_missing`.
  Синтетический ID не создаётся, поскольку его совместимость с последующим webhook
  не установлена. Весь набор сообщений проверяется до атомарной записи страницы.
- Импортированные сообщения не создают заданий и не делают черновики устаревшими.
  Дедупликация использует accountId, integrationId и messageId. Совпадение этих ID
  между историей и webhook проверено автономными фикстурами, но не реальным сравнением.
- После пользовательской проверки API и адаптации кода импорт включён в Settings.
  Он запускается только явно через функцию либо защищённый административный endpoint.

## 6. Отправка сообщения

Источник: предоставленная пользователем 20.11.2026 карточка «Отправка сообщений».
Карточка получена полностью, но содержит противоречия. Пользовательская проверка
текстовой отправки в существующий Instagram Direct подтверждена ответом API и
получением сообщения в Instagram (разделы 6.1 и 11.5).

### 6.1. Обычный ответ в существующий диалог

В заголовке карточки: **`POST /v2/messaging/<lead-id>/messages`**.
В примерах и сноске email: **`POST /v2/messaging/<lead-id>/send`**.
Пользовательская проверка подтвердила `/messages` для обычного текстового ответа
в текущий Instagram Direct. Вариант `/send` отдельно не проверен. Не переключаться
на второй путь автоматически после ошибки/тайм-аута: результат первого запроса
может быть неизвестен.

| Поле | Тип и обязательность по таблице | Назначение |
| --- | --- | --- |
| `authorization` | string, обязательное, headers | accessToken; обычный формат JWT установлен ранее |
| `lead-id` | integer, обязательное, path | ID обращения |
| `message` | object, обязательное | Объект отправляемого сообщения |
| `message.text` | string, необязательное | Текст |
| `message.attachment` | object, отмечено обязательным | Вложение: `type` и `media` |
| `source` | integer, обязательное | Внутренний ID канала `source.realId` |
| `userId` | integer, обязательное | `id` выбранного сотрудника из GET `/v2/managers`, раздел 2.3 |
| `saId` | integer, необязательное | ID интеграции, соответствующей выбранному каналу |
| `customId` | integer, необязательное | Наш идентификатор, возвращаемый в исходящем webhook |
| `replyId` | integer, необязательное | ID цитируемого сообщения |
| `replyMarkup` | object, необязательное | Raw-параметр sendMessage для кнопок Telegram bot |

Сноска разрешает передавать `source.id`, если у канала нет `realId`. Значение должно
совпадать с переданным при загрузке файла. Это fallback для отправки; endpoint истории
в разделе 5 отдельно требует именно `source-real-id` integer в пути.

Сокращённый образец JSON с формой полей из карточки:

```json
{
    "source": "255",
    "userId": 15,
    "saId": 88,
    "customId": "my-identifier",
    "message": {
        "text": "Тестовое сообщение из Python"
    }
}
```

Параметры:

- `leadId` — ID обращения.
- `source` — `source.realId`, при отсутствии использовать `source.id`.
- `saId` — ID интеграции.
- `userId` — ID сотрудника Umnico.
- `customId` — уникальный идентификатор нашего сообщения, возвращается в событии `message.outgoing`.

Все ID условные. Тело выше показывает интересующую нас текстовую часть и не является
проверенным запросом без вложения: полный пример обычной отправки содержит attachment.

**Успешный ответ — массив сообщений.** Полная схема его элементов в этой карточке
не приведена. Клиент требует непустой массив непустых объектов; другие успешные
ответы оставляют попытку в состоянии unknown. Проверка общей формы не является
подтверждением доставки получателю и не вводит неописанные обязательные поля элементов.

В реальном тесте пользователь отправил один запрос на
`/v2/messaging/69258224/messages`: source `81937872` (integer), userId `2583899`,
saId `125653`, строковый customId с префиксом `manual-check-`, только message.text,
без attachment. Получен ответ типа list с одним элементом, после чего пользователь
подтвердил получение сообщения в Instagram. Затем лог backend подтвердил сохранение
исходящего Direct и пропуск lead.changed. Содержимое элемента ответа и исходный
JSON webhook не предоставлены. Поэтому подтверждены доставка текста, приём исходящего
webhook и пригодность этой комбинации параметров для тестового Direct, но не
обработка/возврат customId, серверная идемпотентность или личный ответ на комментарий.

### 6.2. Противоречия карточки отправки

| Вопрос | Таблица | Пример/другой фрагмент |
| --- | --- | --- |
| Путь обычной отправки | `/messages` | `/send` |
| Тип `source` | integer | `"255"`, строка |
| Тип `customId` | integer | `"my-identifier"`, строка; история также описывает string |
| Вложение обычного сообщения | attachment/type/media отмечены обязательными | Отдельный метод outbound показывает текст без вложения; для обычного ответа нужен отдельный ответ/тест |

Пользовательский тест разрешил часть расхождений для текущего Instagram Direct:
`/messages`, integer source и текст без attachment обеспечили доставку. Запрос
содержал string customId, но его возврат и связь с webhook ещё не проверены.
Противоречия карточки сохраняются как сведения источника, а не как требование
проверять другие варианты на уже доставленном сообщении.

`customId` позволяет сопоставлять исходящий webhook с нашим запросом. Карточка не
обещает серверную идемпотентность или защиту от повторной отправки по этому значению.
При неизвестном результате нельзя повторять отправку вслепую.

### 6.3. Шаблоны и инициирование нового диалога

Эти возможности сохранены как справочные; первая версия проекта ограничена текстом.

- Шаблон в существующий диалог: `POST /v2/messaging/{leadId}/send`, в карточке указан
  WhatsApp Business. Тело: `template` с обязательными `namespace` (GUID), `language`
  (`policy`, обычно `deterministic`, и `code`), `name`, необязательным массивом
  `componentValues`; также `source`, `userId`, необязательные `saId`, `customId`, `replyId`.
  Ответ — массив сообщений.
- «Написать первым»: `POST /v2/messages/outbound`. В карточке перечислены WhatsApp
  (2500 сообщений в сутки для новых контактов), Telegram Personal (100 для новых
  контактов) и Mailbox (без ограничений). Это сведения карточки, не проверенные
  текущие лимиты конкретного аккаунта. Поддержка Instagram здесь не подтверждена.
- Для outbound обязательны `message`, `destination`, `saId`, строковый `customId`.
  `destination` — телефон в международном формате, логин Telegram либо email.
  `message` содержит `text` и/или attachment; показан пример только с текстом.
  В таблице attachment снова помечен обязательным, что расходится с этим примером.
  Его тип в таблице — integer, хотя пример с файлом передаёт объект.
  Ответ — массив сообщений. По описанию `customId` вернётся в исходящем webhook,
  но не будет учтён и сохранён Umnico.
- Инициирование шаблоном: тот же `POST /v2/messages/outbound`, WhatsApp Business.
  Передаются `template`, `destination`, `saId`, `customId`. Таблица включает `lead-id`
  как обязательный path-параметр, хотя в URL его нет; отмечает `saId` необязательным
  и `customId` integer, тогда как примеры используют строку. Эти расхождения сохраняются.

Ни обычный outbound, ни WABA-шаблоны не подтверждают сценарий личного ответа на
комментарий Instagram. Для него нужна отдельная карточка или подтверждение Umnico.

### 6.4. Вложения и загрузка файлов — справочно

Типы attachment обычной отправки: `photo`, `doc`, `video`, `mail`, `geo`, `contact`.

- Email: `attachment.type = mail`, поля `to`, `name`, `subject`, `html`, `attachments`.
  Для `/v2/messaging/{leadId}/send` адресат находится в `attachment.to`, а для
  `/v2/messages/outbound` — в `destination` рядом с `message`. В примере вложения
  email содержат `media` с `name`, `size`, `mime`, `type`, `url`.
- Геолокация (`geo`): latitude/longitude; для WhatsApp также name, description, address.
  Для Telegram bot/Telegram personal в карточке перечислены только координаты.
- Контакт (`contact`): name, phone, contactId. Для WhatsApp дополнительно login,
  organizationName, description, vcard; Telegram bot ограничен name/phone/contactId;
  Telegram personal также перечисляет login/organizationName/description/vcard.
- Загрузка: `POST /v2/file`, `Content-Type: multipart/form-data`, обязательный file,
  необязательные source (integer, внутренний ID канала) и saId. Для файла нужно указать
  его MIME Content-Type. В примере source снова передан строкой.
- Ответ загрузки: обязательные `fileId` (GUID), `uploadedAt`, `expiresAt` (date-time).
  Ранний пример отправки использует `media.id/url`, другие — `media.path/name/...`.
  Как именно связать новый ответ fileId с этими примерами media, карточка не объясняет.
  Не выдумывать такой адаптер до сверки; отправка файлов пока вне объёма первой версии.

### 6.5. Проверка номера — справочно

Карточка: `GET /v2/messaging/<saId>/contacts/<distination>/check` — написание
`distination` сохранено из источника. Пример вместо этого использует
`POST /v2/messaging/check-contact` с JSON `saId` и `chatId`.
Расхождение метода/пути не разрешено.

Результаты по HTTP-статусу: 200 — номер существует, 400 — интеграция не поддерживается,
404 — номер отсутствует, 500/504 — ошибка. Карточка ограничивает метод WhatsApp и WABA;
для Instagram и сбора заявки он не требуется.

## 7. Задача для Codex

Текущий этап реализован на Python с существующим синхронным клиентом `requests`,
`python-dotenv`, `loguru` и новым получателем на FastAPI:

- `umnico.py` — вход, проверка вебхуков и интеграций, явная регистрация тестового webhook.
- `webhook_server.py` — приём JSON-событий без предположения об их структуре и без отправки ответов в Instagram.
- `test_umnico.py`, `test_webhook_server.py` — изолированные проверки.

Асинхронный клиент на `httpx` остаётся частью первоначального плана, а не текущей реализации.
Шаблон параметров окружения приведён в разделе 1; существующий `.env` скрипты не переписывают.

Последовательность тестирования (шаги 1–7 подтверждены пользовательскими запусками
и входящими событиями; ответ регистрации с числовым ID отдельно не сохранён):

1. Подготовить действующий JWT для доступа к API: токен из настроек API или строку `accessToken.token`. Для обычного запроса использовать подтверждённый заголовок `Authorization: JWT ...`.
2. Проверить авторизацию через GET `/v2/webhooks/` в `umnico.py`; ожидается массив объектов, допустим и `[]`.
3. Выполнить GET `/v2/integrations`; изучить реальные `id`, `type`, `status` и `identifier`, если он присутствует. Определить подключённые каналы Instagram без предположения об их `type`.
4. Запустить webhook-сервер с публичным HTTPS-адресом.
5. Зарегистрировать тестовый webhook, избегая дублирования.
6. Получить входящее сообщение из Instagram.
7. Подтвердить названия и структуру событий; определить реальные `leadId`, `source`, `saId` и `sa.type`.
8. Запросить каналы обращения и историю сообщений.
9. Отправить тестовый ответ в Instagram.
10. Проверить получение `message.outgoing` и соответствие `customId`.

Логировать HTTP-статусы и тела обычных ответов, исключая токены.
Для login логировать только HTTP-статус: тело может содержать оба токена или отражённые
сервером учётные данные и не должно попадать в лог даже при ошибке.

Не реализовывать пока AI, базу данных, Redis, Celery и сложную архитектуру. Не отправлять сообщения автоматически вне выбранного тестового диалога. При тайм-ауте отправки не повторять запрос автоматически.

## 8. Текущий скрипт и диагностика HTTP 401

Вход по `UMNICO_LOGIN` и `UMNICO_PASSWORD` из окружения или `.env`,
проверка вебхуков и чтение интеграций:

```shell
uv run umnico.py
```

Если оба значения заданы, запуск не требует интерактивного терминала и не запрашивает ввод.
Для явного выбора входа по логину и паролю, в том числе с запросом отсутствующих значений:

```shell
uv run umnico.py --login
```

Скрипт загружает параметры из `.env`, недостающие учётные данные запрашивает в интерактивном терминале,
выполняет один POST `/v2/auth/login` с полями `login` и `pass`, получает `accessToken.token`
и передаёт его последовательно в GET `/v2/webhooks/` и GET `/v2/integrations`.
Старый `UMNICO_API_KEY` не используется. При ошибке первого GET второй не выполняется;
при ошибке второго проверка завершается с кодом 1 без повторного входа.
Если скрытый ввод пароля недоступен, выполнение прекращается до запроса.
Скрипт не выводит пароль и токены, не сохраняет их на диск и не меняет `.env`.
После завершения процесса новый токен не сохраняется для следующего запуска.

Проверка уже имеющегося `UMNICO_API_KEY`, когда `UMNICO_LOGIN` и `UMNICO_PASSWORD` отсутствуют:

```shell
uv run umnico.py
```

В режиме готового ключа скрипт выполняет GET-запросы к `/v2/webhooks/` и `/v2/integrations`
с заголовком `Authorization: JWT ...` из `UMNICO_API_KEY`, без POST login. Используются существующие зависимости
`requests`, `python-dotenv` и `loguru`. Получатель FastAPI запускается отдельно как
`webhook_server.py`; асинхронный REST-клиент ещё не реализован.
Доставка сообщений этой проверкой не проверяется.
Для всех запросов задан явный обработчик `auth`, который сохраняет заголовки и исключает
неявную подмену авторизации через `.netrc` внутри Requests. Настройки прокси и TLS окружения сохраняются.
Перенаправления отключены, тайм-ауты ограничены, автоматических повторов нет.

До добавления режима `--login` при пользовательском запуске получен HTTP `401`
с `error.code = UNAUTHORIZED`.
Это подтверждает отказ сервера в авторизации, но не устанавливает причину отказа.
Теперь `/v2/webhooks/`, метод GET и формат успешного ответа независимо подтверждены
предоставленной карточкой. Менять версию на `v1.3` для устранения этого `401` оснований нет.
Не считать недействительность ключа доказанной только на основании этого ответа.
Для сценариев OAuth 2 предоставленный справочник прямо связывает `401` с истечением `accessToken`.
Если используется такой токен, получать новый нужно выбранным способом из раздела 1.2.
Режим готового ключа не определяет тип токена и не проверяет его срок действия.
Вход с парой логин/пароль получает новый токен, но не обновляет его через `refreshToken`.
При прежней проверке пользователь подтвердил, что значение взято из «Настроек API» Umnico.
При запуске `env -u UMNICO_API_KEY uv run umnico.py` отказ `401` сохранился.
Не переносить объяснение об истечении OAuth `accessToken` на этот токен без дополнительных данных.

Порядок диагностики:

1. Использовать подтверждённый GET `/v2/webhooks/` и заголовок `Authorization: JWT <token>`.
   Эти части текущего скрипта соответствуют предоставленному справочнику.
2. Проверить источник токена: JWT нужного аккаунта из настроек API или строка `accessToken.token`.
   Убедиться, что в `UMNICO_API_KEY` не подставлен JSON-объект `accessToken`, `pluginToken` или `refreshToken.token`.
   Для истёкшего OAuth `accessToken` выполнить соответствующую процедуру из раздела 1.2.
3. Учесть приоритет источников: `load_dotenv(..., override=False)` сохраняет уже заданные
   переменные процесса. Значения `UMNICO_LOGIN`, `UMNICO_PASSWORD` и `UMNICO_API_KEY` в терминале
   могут перекрывать соответствующие значения `.env`.
4. Для получения нового токена задать пару `UMNICO_LOGIN` / `UMNICO_PASSWORD`
   и запустить `uv run umnico.py` либо использовать `uv run umnico.py --login` с ручным вводом.
   После успешного входа GET выполняется автоматически. Если отказ сохраняется,
   передать поддержке Umnico время запроса, метод, путь, HTTP-статус и `traceId` из ответа.
   Не передавать значение ключа в переписку, документацию или Git.

Для ручного запуска в macOS/zsh без унаследованного значения переменной терминала:

```shell
env -u UMNICO_API_KEY uv run umnico.py
```

Команда убирает `UMNICO_API_KEY` только из окружения этого запуска; `umnico.py` затем загружает `.env`
рядом со скриптом. Она не меняет файл `.env` и не отключает приоритет пары логин/пароль.

Для дальнейшей реализации ещё нужны выдержки или уточнения официального справочника:

- Для сценария plugin token: получение исходного `accessToken`, который требует таблица этого метода.
  Login по логину и паролю без заголовка `Authorization` уже подтверждён пользовательским запуском.
- Вебхуки: допустимые названия событий и поведение POST/PUT без `events`,
  а также тип `status` в PUT. Основные методы, поля, ответы и ограничение в 10 записей установлены в разделе 3.
- Сообщения: актуальные методы каналов, истории и отправки, а также полный контракт событий.
  Наблюдаемые структуры Direct, комментария и изменения обращения уже описаны в разделе 4.

## 9. Получение первого webhook через tuna

### 9.1. Запуск получателя

В первом терминале из каталога проекта:

```shell
uv run webhook_server.py
```

По умолчанию сервер слушает `127.0.0.1:8080`, соответствуя указанному пользователем порту tuna.
Параметры `--host` и `--port` позволяют изменить привязку при необходимости.
Маршруты:

- GET `/health` — HTTP 200 и `{"status":"ok"}`.
- POST `/webhooks/umnico` — приём JSON, запись события с маскированием токенов и паролей, HTTP 200.
- Некорректный JSON — 400, тело больше 1 МиБ — 413, чтение дольше 10 секунд — 408.

Зависимости объявлены в начале скрипта в формате PEP 723: FastAPI, Uvicorn, Loguru,
Requests и python-dotenv (последние нужны для импорта общего маскирования из `umnico.py`).
При первом запуске uv создаёт отдельное окружение скрипта и устанавливает зависимости;
зависимости проекта при таком запуске не используются. `pyproject.toml` и проектный `uv.lock`
этой реализацией не меняются. Отдельный lock-файл скрипта пока не сформирован.
[Описание inline-зависимостей uv](https://docs.astral.sh/uv/guides/scripts/#declaring-script-dependencies).

Получатель не загружает `.env`, не вызывает API Umnico и не отправляет сообщения.
События выводятся в терминал и в `logs/umnico_webhook.log` в формате JSON-записей Loguru.
Ротация — 5 МБ, сохраняются три старых файла; каталог `logs/` исключён из Git.
Тела сохраняются с маскированием секретных полей, значение JWT в тексте также скрывается.
Заголовки входящего запроса не логируются. Схема и подпись webhook пока не проверяются:
на первом этапе события используются только для наблюдения, а не для запуска действий.

### 9.2. Туннель tuna

Пользователь уже настроил tuna на `127.0.0.1:8080`; текущий процесс туннеля оставить запущенным.
Если туннель нужно запустить заново, стандартная команда:

```shell
tuna http 8080
```

Использовать HTTPS-адрес из вывода tuna. Команда, параметры адреса и поведение динамического
URL описаны в [официальном справочнике HTTP-туннелей tuna](https://tuna.am/docs/tunnels/http/).
Для первоначальной проверки не включать дополнительную Basic Auth или проверку `X-Token`,
поскольку передача таких данных из Umnico предоставленными методами не описана.
Не использовать режим файлового сервера для каталога проекта.

После запуска получателя проверить health HTTP-клиентом, например:

```shell
curl --fail --show-error https://YOUR-TUNA-HOST/health
```

Ожидается `{"status":"ok"}`. Заменить `YOUR-TUNA-HOST` фактическим хостом из вывода tuna.
Для webhook использовать **полный** адрес `<HTTPS-адрес-tuna>/webhooks/umnico`, а не корень домена.
Если динамический адрес туннеля изменится, прежний webhook не будет указывать на новый туннель.
Существующие записи автоматически не редактируются и не удаляются.

### 9.3. Регистрация тестового адреса

После успешной проверки `/health` во втором терминале:

```shell
uv run umnico.py --register-webhook --webhook-url https://YOUR-TUNA-HOST/webhooks/umnico
```

Заменить `YOUR-TUNA-HOST` фактическим хостом tuna. Альтернатива — задать `UMNICO_WEBHOOK_URL`
в своём `.env` и выполнить `uv run umnico.py --register-webhook`.
`--webhook-url` имеет приоритет над переменной окружения и требует флага `--register-webhook`.
Обычный запуск `uv run umnico.py` по-прежнему не создаёт вебхуков.

Команда выполняет вход и обычные GET-проверки, затем:

1. Ищет запись с тем же URL в уже полученном списке; учитывает регистр хоста, порт HTTPS 443
   и конечный `/`. Существующая запись повторно не создаётся.
2. Для отключённой существующей записи выводит предупреждение, не изменяя её.
3. Если совпадения нет и записей уже 10, завершает работу без POST.
4. Иначе выполняет один POST `/v2/webhooks/` с `url`, именем `Python Test Bot` и `events: []`.
5. Проверяет ID и URL ответа. Ошибка, тайм-аут или неоднозначный ответ не запускают повторный POST;
   перед повторным созданием нужно прочитать список и проверить, не появилась ли запись.

URL должен быть HTTPS и иметь путь `/webhooks/umnico`, без логина, пароля, query и fragment.
Локальные адреса и непубличные IP в таком URL отклоняются; DNS-доступность скрипт не проверяет.
Создание не изменяет остальные вебхуки. Из-за гонки с другим клиентом даже при локальной проверке
сервер может вернуть 400 при достижении лимита — это обрабатывается как ошибка без повтора.

### 9.4. Проверка входящего события

в подключённый Instagram с другого аккаунта и проверить терминал получателя или файл лога.
Фактический JSON `message.incoming` уже получен пользователем; подтверждённые пути полей
и тип `message.sa.type: "instagramV3"` приведены в разделе 4.

### 9.5. Подтверждённое входящее сообщение

20.11.2026 пользователь предоставил вывод получателя с тремя JSON-событиями:
`customer.created`, `lead.created` и `message.incoming`. Последнее содержит выбранный тестовый текст,
`incoming: true`, внутренний ID источника и параметры интеграции Instagram.
Сообщение поступило в обращение, указанное в обоих событиях `lead.created` и `message.incoming`.
Подтверждена доставка событий до локального обработчика через настроенный пользователем туннель.

Позднее в тот же день пользователь предоставил `lead.changed` со ссылкой на пост в тексте
и ещё одно `message.incoming` — комментарий с `source.type: "comment"`, текстом, URL поста
и объектом `preview`. Ссылка указывала на тот же пост в обоих событиях.
Тип интеграции остался `instagramV3`; Direct и комментарий имели разные источники в одном обращении.
Таким образом подтверждён приём как Direct, так и комментариев, включая контекст поста
в проверенном событии комментария. Устройство этих данных описано в разделах 4.1–4.3.

Полный ответ команды регистрации и числовой ID записи webhook в этом логе не представлены;
получение событий не используется как замена отдельной проверке GET `/v2/webhooks/`.
Причина первоначального отказа старого токена остаётся не установлена, но выбранный сценарий login
с новым токеном и приём входящих сообщений уже работают по пользовательским результатам.

Дальше сверить актуальные методы каналов обращения и истории, затем получить историю выбранного
тестового диалога. До отправки ответа определить действительный `userId` сотрудника Umnico.
Отправка сообщений и получение `message.outgoing` с `customId` ещё не проверены;
получатель не отправляет ответы автоматически.

### 10.3. Конфигурация и жизненный цикл доступа

1. Задать секреты через окружение или локальный файл, исключённый из Git. Использовать имена
   `UMNICO_LOGIN`, `UMNICO_PASSWORD`, `UMNICO_API_KEY` из раздела 1; реальные значения не копировать
   в документацию, примеры и тесты. Переменные процесса имеют приоритет над `.env`.
2. Для проверенного сценария выполнить login с `{"login": "...", "pass": "..."}` без исходного
   `Authorization`. В обычные API-запросы передавать строку `accessToken.token` с одним префиксом `JWT`.
   Не использовать `Bearer`, `refreshToken`, `pluginToken` или `message.source.token` вместо неё.
3. Текущий CLI получает новый токен на каждый запуск в режиме login. Для длительно работающего
   приложения отдельно реализовать хранение токенов в памяти и обновление по `expiresAt`/refresh
   из раздела 1.2; повторный login для каждого входящего webhook текущей схемой не требуется.
   `get_access_token` сейчас возвращает только строку и не сохраняет сроки и `refreshToken`.
4. Сохранить ограниченные тайм-ауты клиента `(5, 20)` секунд (подключение, чтение), отключение
   перенаправлений и явную авторизацию, предотвращающую подмену JWT данными `.netrc`.
   Не включать автоматический повтор изменяющих запросов при неизвестном результате.
5. Задать актуальный `UMNICO_WEBHOOK_URL` с HTTPS и путём `/webhooks/umnico`.
   Тестовый временный домен tuna не является постоянной настройкой основного проекта.
   Команды запуска и регистрации приведены в разделе 9; один лишь GET `/health` ещё не проверяет
   обработку POST или подлинность отправителя.

### 10.4. Данные для обработки сообщения

Это рекомендации для будущего адаптера, а не уже реализованная модель или полный контракт Umnico.
Читать поля с проверкой типа и наличия; неизвестные типы событий сохранять для диагностики,
не превращая их автоматически в команды отправки.

| Данные основного проекта | Откуда брать |
|---|---|
| Аккаунт и обращение | `accountId`, `leadId` |
| Тип события | Корневой `type`; для сообщения ожидается `message.incoming` |
| Направление | `message.incoming`; обработку входящего сообщения ограничить значением true |
| ID и время сообщения | `message.messageId` как строка, `message.datetime` |
| Интеграция | `message.sa.id`, `message.sa.type`, дополнительно `message.source.saId` |
| Контекст источника | Сохранять отдельно `message.source.type`, `realId`, `id`, `identifier` |
| Автор сообщения | `message.sender.id`, `customerId`, `socialId`, `login`, если присутствуют |
| Текст сообщения или комментария | `message.message.text` |
| Пост для комментария | `message.message.url`, дополнительно `message.preview.url` |
| Дополнительные сведения о посте | `message.preview.description`, `owner`, `photo`, если присутствуют |
| Состояние обращения | `lead` из `lead.created` / `lead.changed`; текст снимка — `lead.message.data.text` |

Для локальной маршрутизации сохранять сочетание аккаунта, обращения, интеграции и источника;
не хранить единственный `source` на весь `leadId`. Признак Direct/комментария в проверенном канале —
`source.type`, а не общий `sa.type: "instagramV3"`. Для прочих типов источников нужна отдельная обработка.
Контекст поста в `preview` относится к посту; текст пользователя берётся из `message.message.text`.
URL в обычном тексте без `source.type: "comment"` сам по себе не означает комментарий.

Сохранять числовые внутренние ID и строковые внешние ID раздельно. `sender.id`, `customerId`
и `socialId` не являются ID сотрудника Umnico. `lead.userId` в полученных событиях был null;
значение `UMNICO_USER_ID` для будущей отправки ещё требуется определить.
Не собирать адрес отправки или идентификатор API из частей строки `source.id`.

Перед добавлением побочных действий предусмотреть обработку повторной доставки.
Кандидат для локального ключа сообщения — сочетание `accountId`, `message.sa.id`, `source.type`
и `message.messageId`; уникальность и стабильность этого сочетания при повторе ещё нужно проверить.
`webhookId` не использовать как числовой ID зарегистрированного webhook; его гарантий уникальности
и стабильности для устранения повторов предоставленная документация не устанавливает.
Не запускать вторую обработку сообщения по его снимку в `lead.changed`.

### 10.5. Приём и проверка после переноса

Текущий сервер — диагностический получатель: принимает любой корректный JSON, включая массивы,
маскирует секреты и возвращает HTTP 200. Подпись, принадлежность аккаунту и схема не проверяются.
До подключения действий основного проекта нужно уточнить поддерживаемый Umnico способ проверки
подлинности webhook и реализовать его по актуальному контракту, не предполагая существование
неописанного заголовка подписи. Маскирование токенов не обезличивает текст, профили и другие
данные клиента; настроить доступ и срок хранения журналов по правилам основного проекта.

При переносе сначала выполнить изолированные проверки из раздела 8.1 в штатном Python 3.12+
с настоящими зависимостями. В существующих 61 проверке нет отдельных сценариев извлечения поста,
маршрутизации Direct/комментариев, устранения повторов или отправки ответа: эта логика ещё не написана.
При её добавлении использовать обезличенные примеры раздела 4 как основу фикстур и проверить
разные источники в одном обращении, отсутствие `preview` и `lead.changed` с тем же текстом.

Затем в выбранном тестовом аккаунте вручную проверить login, список интеграций, публичный `/health`,
фактическую запись webhook и получение новых Direct/комментария. Локальные ID из примеров не переносить
в конфигурацию: получать их из интеграций и событий нового окружения.
Для дальнейшего двустороннего обмена сначала сверить методы истории и отправки и определить
сотрудника, затем отдельно проверить ответ в нужном контексте и доставку в Instagram.
Входящий комментарий сам по себе не подтверждает возможность ответа на него или отправки в Direct.

### 11.1. Запуск, секреты и регистрация webhook

- Запуск: `mise run start`, без аргументов приложения. Вводить параметры через
  `--env-file`, `--serve`, `--register-webhook` или `--webhook-url` больше не требуется;
  эти режимы в основном проекте не реализованы.
- `config.py` автоматически читает проектный `.env`. В нём только секреты:
  UMNICO_LOGIN, UMNICO_PASSWORD, UMNICO_API_KEY, OPENROUTER_API_KEY, ADMIN_TOKEN,
  WEBHOOK_TOKEN. Прочие настройки задаются через `Settings` в Python.
  Секреты процесса имеют приоритет над файлом, интерполяция выключена.
- Сгенерировать токены можно вручную, независимо от запуска приложения:
  `mise exec -- uv run --no-sync python scripts/generate_admin_token.py` и
  `mise exec -- uv run --no-sync python scripts/generate_webhook_token.py`.
  Скрипты печатают строки для ручного переноса в `.env`, не читают и не меняют его.
  ADMIN_TOKEN и WEBHOOK_TOKEN должны быть независимыми; это не токены Umnico.
- При обычном запуске нужны WEBHOOK_TOKEN и учётные данные Umnico. Программа каждый
  раз запрашивает актуальный публичный HTTPS-адрес туннеля без пути и токена;
  адрес не сохраняется в `.env`. Затем добавляет `/webhooks/umnico/<WEBHOOK_TOKEN>`.
- По умолчанию API слушает `127.0.0.1:8000`; туннель должен направлять запросы
  на этот порт. `GET /health` возвращает `{"status":"ok"}`.
- После готовности локального API выполняется GET `/v2/webhooks/`. Совпадающий
  активный URL используется; при отсутствии выполняется один POST с url, name
  и `events: []`. Другие записи не изменяются и не удаляются. Совпадающая отключённая
  запись либо лимит webhook дают ошибку. После неизвестного результата нет слепого
  повторного POST: следующий запуск сначала проверит список.
- Регистрация логирует результат и числовой ID записи, но не полный URL с токеном.
  Access-log Uvicorn выключен; туннель/прокси также не должен раскрывать секретный путь.
- Административные операции требуют `Authorization: Bearer <ADMIN_TOKEN>`.
  Приём webhook проверяет секрет в пути. Это защита доступа по известному URL,
  а не подтверждённая криптографическая подпись Umnico. Контракт подписи не получен.

### 11.3. Реализация шага 2 после реальных проверок

- Добавлены list_managers() и list_threads() по проверенным GET-путям. Из каналов
  возвращаются только нужные поля без token. Если у локального чата нет realId,
  приложение ищет единственный положительный realId по внешнему id, типу и saId.
  Отсутствующий или неоднозначный маршрут не подменяется первым найденным каналом.
- История использует отдельный адаптер sentAt, integer cursor, проверку канала,
  распознавание пустого конца и ограничения раздела 5.3. Сохраняется атомарно
  по страницам, без заданий на старую переписку.
- Отправка использует `/messages`, integer source/saId/userId, string customId
  и message.text без attachment. Ответ проверяется как непустой массив объектов.
  Автоматического повтора и fallback на `/send` нет.
- `MessageEvent.custom_id` читает customId исходящего сообщения либо оболочки
  события. При наличии обоих значения должны совпадать. Входящий customId не
  подтверждает исходящую попытку. Реальное расположение поля ещё не предоставлено;
  обе поддержанные формы проверены синтетическими фикстурами.
- `outgoing_receipts` хранит customId отдельно от контекста; исходный JSON и token
  не сохраняются. Таблица и индекс создаются идемпотентно без ALTER существующих
  таблиц. Пользовательская БД во время доработки не открывалась и не изменялась.
- Совпадающий исходящий receipt с тем же request_id, локальным чатом и текстом
  переводит попытку в sent. Поздний webhook разрешает unknown, в том числе после
  перезапуска. Дубликат может дополнить ранее сохранённое сообщение customId.
  Несовпадающие аккаунт/интеграция/маршрут/текст не подтверждают другую попытку.
- Receipt, пришедший до HTTP-ответа, не отменяется последующим тайм-аутом/ошибкой.
  Повтор request_id возвращает сохранённое состояние без HTTP, даже если для нового
  запроса понадобилось бы заново получать маршрут. Sent — принятие API/исходящее
  событие, а не универсальная гарантия доставки в Instagram.
- Ручная отправка ставит чат на паузу и делает черновики устаревшими. Unknown
  блокирует новые отправки до подтверждающего receipt; активное задание также
  блокирует ручной ответ. AI-обработка относится к шагу 3.
- `umnico_history_verified=True`, `umnico_send_verified=True` включены после
  реальной проверки Direct и автономной проверки адаптации. `umnico_user_id="2583899"`
  явно выбран по доставленному пользовательскому тесту. Для другого аккаунта нужно
  явно изменить сотрудника в Python; в `.env` остаются только секреты. При старте
  выполняется регистрация webhook, но не импорт истории или отправка текста.

### 11.4. Границы завершения и дальнейшая реальная проверка

Реализация шага 2 для проверенного Direct завершена и проверяется автономными
тестами клиента, временной SQLite и административного API. Результаты команд
указаны в IMPLEMENTATION_PROGRESS.md. Реальные операции раздела 11.5 выполнял
пользователь до этой адаптации; Codex реальные API и постоянную БД не использует.

- Реальный импорт обновлённым приложением, содержимое sentAt и сопоставление
  messageId истории/webhook ещё не сравнивались. Записи без messageId явно
  отклоняются, а не получают выдуманный идентификатор.
- Возврат конкретного customId в реальном webhook ещё не показан. Код корреляции
  проверен автономно, но существующие сообщения не позволяют восстановить поле,
  которое прежний парсер не сохранял. Для отдельной проверки нужна новая явно
  согласованная отправка через приложение и повтор её request_id без нового POST
  в Umnico. Не повторять прежний ручной `_request`: он обходил журнал попыток.
- Для личного ответа после комментария нет подтверждённого метода. Отправка
  заблокирована с `comment_private_reply_unverified`; источник и причина сохраняются
  для будущей панели. Это отсутствие проверки, а не доказательство недоступности API.
  Публичный ответ и outbound не подставляются вместо личного.
- История требует положительный realId. Внешний source.id без realId для отправки
  описан карточкой, но не проверен для этого Instagram: если не найден подходящий
  внутренний канал, сохраняется причина missing_source_real_id/ambiguous_source_real_id.
- Контракт криптографической подписи Umnico не получен. Пока используется отдельный
  секретный URL webhook с проверкой токена и отключённым access-log; подпись не выдумана.

Эти границы не означают реализацию шагов 3–4: AI-исполнителя и панели пока нет.
